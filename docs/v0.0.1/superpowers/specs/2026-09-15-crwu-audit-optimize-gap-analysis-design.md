# crwu-audit-optimize AI—人工差距分析设计

## 1. 背景

`crwu-audit` 已能在阶段二把 AI 独立审核结果与人工复核记录分为共同命中、AI 新增、结论分歧和人工独有，并对人工独有项做在件核验。`crwu-audit-optimize` 已负责从漏检、误检和复核反馈诊断知识库、词表、Skill 算法或结构映射问题。

当前缺口是两者之间没有稳定的复盘交付物：用户无法从一份报告中直观看到哪些人工独有事项是真实 AI 漏检、每条漏检发生在执行链的哪个环节、应补哪个知识库文档或修改哪个 Skill，以及修复计划覆盖了哪些原始漏检。

本设计不新增 Skill，而是在 `crwu-audit-optimize` 内增加“AI—人工差距分析模式”，并用固定 HTML 模板交付分析结果和修复计划。

## 2. 目标与非目标

### 2.1 目标

- 审核完成后读取 AI 冻结结果、人工复核文件、被审最终版材料和本项目知识库工作集，逐条对比 AI 与人工意见。
- 先验证人工独有项是否在最终版材料中仍然存在，再判断是否属于 AI 漏检。
- 对真实漏检重建“材料读取 → 画像 → 路由 → 知识装配 → Skill 执行 → 输出”链路，给出有证据的根因。
- 同时使用本次审核实际下载的知识库快照和当前最新知识库，分别回答“当时为什么漏检”和“缺口现在是否仍存在”。
- 生成固定的单文件 HTML 报告，用表格承载逐条证据，用 ECharts 展示差距规模、根因分布和漏检到修复计划的关系。
- 给知识库缺口生成可直接执行的人工修复单；给已批准的源仓 Skill 改动生成可复制给 AI 的执行 Prompt。
- 建立人工独有事项、根因和修复计划之间的双向追溯，支持一对多和多对一关系。

### 2.2 非目标

- 不在差距分析阶段修改知识库、Skill、注册表或运行时目录。
- 不允许任何 CLI、`crwu-dws` 或 `crwu-audit-optimize` 流程写入知识库。
- 不把人工复核意见自动视为正确结论。
- 不把人工复核内容回写、伪装或补造成阶段一 AI 独立发现。
- 不新增 `crwu-audit-*` Skill；结构和映射问题仍交给 `crwu-audit-skill-maintainer`。
- 不把知识库正文复制进 Skill。

## 3. 模式边界

`crwu-audit-optimize` 增加三个明确模式：

1. **差距分析模式**：只读输入、形成 HTML 报告和修复计划，不修改任何权威内容。
2. **普通反馈优化模式**：保留现有反馈定位、根因分桶和《优化方案》流程。
3. **批准后执行模式**：只执行用户明确批准的源仓 Skill 改动；知识库计划永久为人工处理。

差距分析报告可以作为后续《优化方案》的结构化输入。当报告已经包含逐文件目标、修改说明、依赖、验证和风险，用户对具体计划 ID 的明确批准可满足“先方案、后执行”门禁，无需重复生成一份同义方案。若实际状态与报告基线不一致或需要扩大文件范围，必须停止并重新提交方案。

## 4. 输入与前置校验

### 4.1 必需输入

- AI 阶段一冻结结果，优先读取 `AuditResult` JSON 或 HTML 内嵌的同源 JSON。
- 人工复核文件及其文件级、页码、段落、行号或单元格出处。
- 被审最终版材料；如人工意见附答复文本，还需取得答复和对应最终版。
- 本项目 `knowledge/` 工作集和 `.crwu-manifest.jsonl`。
- 本次审核的 `route_profile`、实际加载的 `source_skills[]`、规则快照、装配记录和未检查项。
- 相关 Skill 的源仓或已安装只读副本，用于分析其适用边界、装配表和执行流程。

### 4.2 同一项目证明

本地知识库正文只能在同一审核项目的差距分析中复用。分析前必须核对案例目录、manifest、AuditResult 中的项目标识、知识路径、`nodeId` 和 `exportedAt`。无法证明属于本次审核时，不得把该正文作为历史归因证据。

### 4.3 缺失处理

- 无 AI 冻结结果：停止差距归因，报告“无法证明 AI 当时输出”。
- 无人工复核出处：保留为待核验人工事项，不进入真实漏检统计。
- 无最终版材料：标记 `L-uncheckable`。
- 无 manifest 或本次知识工作集不完整：可分析画像、路由和 Skill，但知识装配结论必须标记不确定。
- 相关文件不可读：记录具体失败，不以“未发现问题”代替。

## 5. 分析流程

### 5.1 双方意见标准化与匹配

AI finding 和人工复核事项统一提取：问题对象、问题事实、适用文件、材料位置、规则依据、整改动作和严重度。匹配结果保留以下类型：

- `A / overlap`：AI 与人工均发现。
- `B / ai_only`：仅 AI 发现。
- `C / divergent`：双方涉及同一事项但事实、范围或结论不同。
- `L / reviewer_only`：仅人工提出，进入在件核验。

匹配必须保留两端原始出处和匹配理由；不得仅凭标题或关键词判定相同。

### 5.2 人工独有项在件核验

每条 `L` 必须先检查被审最终版：

- `L-resolved`：最终版已落实，不计 AI 漏检。
- `L-open`：最终版仍存在，进入根因分析。
- `L-unclosed`：答复称已整改但最终版未落实，优先反馈客户，同时进入根因分析。
- `L-uncheckable`：材料缺失或不可读，不作漏检判断。
- `L-questionable`：人工意见与材料或权威依据不一致，列明冲突，交人工确认。

只有 `L-open` 和 `L-unclosed` 进入确认漏检统计与修复计划。

### 5.3 执行链重建

对每条确认漏检逐层核验：

1. **输入读取**：相关文件、压缩包、工作表、隐藏区和最终版是否进入工作集并真实读取。
2. **画像识别**：形态、对象、业务、方法、监管覆盖和材料分区是否识别正确。
3. **路由分发**：应加载的资产、业务、公共、数据和监管能力是否实际加载。
4. **知识装配**：装配表是否包含目标路径，manifest 是否下载成功，正文是否可读。
5. **知识内容**：本次下载正文是否包含适用的 RULE/CHK、条件、步骤和判断标准。
6. **Skill 执行**：相关 Skill 是否把 RULE/CHK 转换成可执行检查步骤和证据要求。
7. **实际执行**：检查记录是否证明步骤被执行；缺少执行证据不能视为已检查。
8. **输出呈现**：finding 是否被错误去重、过滤、合并、降级或渲染丢失。

每层保存 `passed | failed | unknown | not_applicable`、证据出处和解释。根因不能只写结论标签。

## 6. 双基线知识库分析

### 6.1 历史基线

本项目 `knowledge/` 和 manifest 用于还原 AI 审核当时实际看到了什么。历史基线必须展示库内路径、本地案例相对路径、`nodeId`、`exportedAt`、下载状态和正文定位。它不能跨项目复用。

### 6.2 当前基线

通过 `crwu-dws` 只读重新下载目标文档最新正文，用于判断缺口是否已经被人工补齐。当前正文不得反向替代历史基线，也不得据此宣称 AI 当时本应看到后来新增的内容。

### 6.3 结论组合

- 历史缺失、当前仍缺失：有效知识库修复项。
- 历史缺失、当前已补齐：记录为“已外部修复”，只做回归，不重复提修复。
- 历史已有、Skill 未执行：Skill 或执行链问题，不列为知识库缺失。
- 历史与当前均有、步骤也执行：继续检查证据检索、去重和输出环节。
- 任一基线不可证明：降低置信度并列人工确认项。

## 7. 根因分类

| 代码 | 含义 | 默认后续 |
| --- | --- | --- |
| `K1` | 知识库没有适用规则、案例或检查点 | 生成知识库人工修复单 |
| `K2` | 知识库已有相关内容，但条件、证据、步骤、标准或例外不足 | 生成知识库人工修复单 |
| `S1` | 现有 Skill 的职责范围未覆盖该方向 | 扩展现有 Skill，必要时交维护器 |
| `S2` | Skill 已覆盖但适用条件、算法、步骤或证据要求不合理 | 生成源仓 Skill 修复计划 |
| `R` | 路由、registry、classification 或装配映射错误 | 交 `crwu-audit-skill-maintainer` |
| `I` | 材料盘点、解压、解析、隐藏区或表格读取失败 | 修改输入或 datacheck 流程 |
| `E` | 知识和步骤均存在，但本次执行没有完成或没有证据 | 加强执行门禁和检查留痕 |
| `O` | 已形成 finding，但去重、过滤、合并或渲染丢失 | 修复输出链 |
| `H` | 已整改、不可核验、人工意见存疑或不是 AI 漏检 | 不进入修复执行 |

一条漏检可以有多个根因，但必须区分主因和促成因素，避免为同一事实生成互相重复的计划。

## 8. 追溯数据模型

差距分析产物至少包含以下逻辑结构：

```json
{
  "report_id": "GAP-BG8169-20260915",
  "baselines": {
    "audit_snapshot": {},
    "current_kb_snapshot": {}
  },
  "reviewer_only_items": [
    {
      "gap_id": "L-01",
      "reviewer_evidence": {},
      "final_document_verification": {},
      "status": "L-open",
      "execution_trace": [],
      "root_causes": ["K2", "S2"],
      "linked_fix_ids": ["FIX-KB-01", "FIX-SKILL-02"]
    }
  ],
  "repair_plans": [
    {
      "fix_id": "FIX-KB-01",
      "type": "kb_manual",
      "source_gap_ids": ["L-01"],
      "target": {},
      "change_spec": {},
      "dependencies": [],
      "validation": [],
      "approval_state": "pending"
    }
  ]
}
```

追溯约束：

- 每个进入执行的 `L-*` 至少关联一个 `FIX-*` 或明确的“不修复理由”。
- 每个 `FIX-*` 必须反向保存非空 `source_gap_ids[]`。
- 支持一个 `L-*` 对多个 `FIX-*`，也支持一个 `FIX-*` 覆盖多个 `L-*`。
- 修复回归按 `source_gap_ids[]` 逐条核验，不以测试整体通过替代原问题验证。

## 9. HTML 报告设计

### 9.1 交付形式

- 使用固定模板 `template/gap-analysis-report.html`。
- 最终交付为一个自包含 HTML，可离线打开和 A4 打印。
- ECharts 运行时代码随 Skill 保存，由渲染器内联进最终 HTML；报告不得依赖公网 CDN。
- 报告数据由结构化 JSON 注入，模板只负责呈现，不得在渲染阶段改变归因或修复结论。
- 本地文件展示案例相对路径，不暴露个人绝对路径；知识库展示库内层级路径和 `exportedAt`。

### 9.2 页面结构

1. 项目与基线信息。
2. 差距摘要：人工复核数量、共同发现、AI 新增、人工独有、确认漏检、已整改和不可核验。
3. ECharts 差距构成图。
4. ECharts 根因分布图。
5. 人工独有事项逐条归因表。
6. 单项执行链和两端证据详情。
7. ECharts“人工独有事项 → 根因 → 修复计划”桑基图。
8. 人工独有事项与修复计划对应表。
9. 知识库人工修复单。
10. Skill 修复计划、批准选择和可复制执行 Prompt。
11. 修复依赖、验证步骤、风险和未处理事项。

表格是证据主载体，ECharts 只用于汇总、分布和关系展示，不替代表格中的逐条证据。

### 9.3 交互

- 按状态、根因、责任方和修复计划筛选。
- 点击 `L-*` 或图表节点时聚焦对应证据和 `FIX-*`。
- 点击 `FIX-*` 时反向展示它覆盖的所有 `source_gap_ids[]`。
- 知识库人工修复单可单独复制。
- Skill 修复计划可勾选；页面仅为批准项生成执行 Prompt。
- 浏览器复制失败时保留可选择文本，不影响报告阅读和打印。

## 10. 修复计划与权限门禁

### 10.1 知识库人工修复单

每个 `kb_manual` 计划必须给出：

- 计划 ID 和对应 `source_gap_ids[]`。
- 精确库内文档路径。
- 定位锚点，例如 RULE/CHK 编号和相邻条目。
- 当前内容为什么不足，以及历史、当前双基线证据。
- 建议扩写、替换或新增的方式。
- 建议补充的内容结构：适用条件、必取证据、检查步骤、判断标准、异常输出、例外和证据要求。
- 编号、词表、批次 README、进度表、装配表和总纲的联动判断。
- 人工完成凭证和 AI 后续只读核验步骤。

知识库的新增、编辑、移动和删除一律标记 `manual_only`。报告不得生成或执行任何知识库写入命令，也不得调用其他 Skill 绕过 CLI 边界。

### 10.2 Skill 修复执行 Prompt

AI 可执行 Prompt 必须包含：

- 报告编号、用户明确批准的 `FIX-*` 和对应 `source_gap_ids[]`。
- 精确源仓文件和逐文件修改目标。
- 执行前重新检查源仓状态；依赖知识库修复时，先通过 `crwu-dws` 只读核验人工改动。
- 只修改批准清单内文件，不写运行时 Skill 目录。
- 不复制知识库正文，只保存 RULE/CHK 编号和库内路径寻址键。
- 最新状态冲突、路径变化、需要新增文件或扩大范围时立即停止。
- 具体校验、装配复现、原漏检回归和完成汇报要求。

复制 Prompt 本身不代表授权。只有 Prompt 中保留用户明确表达的“我确认执行”以及具体批准计划 ID，才能进入批准后执行模式。

### 10.3 依赖门禁

如果一个 Skill 修复依赖知识库先补齐：

1. 知识库计划状态必须由用户更新为“人工已完成”。
2. AI 通过 `crwu-dws` 只读重新下载目标正文并验证预期内容。
3. 验证通过且用户批准 Skill 计划后，才允许修改源仓。
4. 验证失败时报告差异，不自动改知识库或调整计划目标。

## 11. 建议实现结构

现有 Skill 保持入口化，新增细节按需加载：

```text
crwu-audit-optimize/
├── SKILL.md
├── references/
│   ├── 00-优化规范与文件落点.md
│   ├── 01-反馈定位与画像流程.md
│   ├── 02-方案模板与确认门禁.md
│   └── 03-AI人工差距分析流程.md
├── scripts/
│   ├── gap_analysis_delivery.py
│   ├── gap_analysis.schema.json
│   └── test_gap_analysis_delivery.py
└── template/
    ├── gap-analysis-report.html
    ├── echarts.min.js
    └── NOTICE.echarts.txt
```

- `SKILL.md`：增加模式选择、输入、执行摘要和权限边界。
- `references/03`：保存本设计中的匹配、在件核验、执行链、双基线、根因和追溯规则。
- `references/02`：补充差距分析报告如何进入确认门禁，以及知识库人工/Skill AI 两类计划模板。
- renderer：校验结构化 JSON 后确定性渲染，不修改分析结论。
- schema：约束 ID 唯一性、双向关系完整性、知识库计划 `manual_only` 和批准状态。
- template：保存表格、图表、筛选、复制和打印布局。
- ECharts：固定版本并保留对应许可证声明；渲染器只从本 Skill 内读取并内联，不访问外部网络。

## 12. 错误处理

- 任一图表数据缺失时显示“数据不足”，表格和证据仍可阅读。
- ECharts 初始化失败不影响表格、修复单和 Prompt 展示。
- schema 校验失败时不得生成正式报告，应逐条返回字段错误。
- Prompt 中出现知识库写入动作、未批准计划或未知 `FIX-*` 时校验失败。
- `source_gap_ids[]` 或 `linked_fix_ids[]` 断链时校验失败。
- HTML 中出现个人绝对路径、凭据、知识库写命令或运行时目录写入指令时校验失败。

## 13. 验证与回归

实现完成后至少验证：

1. Skill frontmatter、references 路由和自包含性校验通过。
2. gap analysis schema 的合法、缺字段、断链、重复 ID、越权 Prompt 用例。
3. HTML 渲染包含全部表格、图表数据、人工修复单和批准后 Prompt。
4. 无网络条件下图表仍可显示，打印布局不丢失主表和修复计划。
5. 一个漏检对应多个计划、一个计划覆盖多个漏检的双向关系正确。
6. `L-resolved`、`L-uncheckable` 和 `L-questionable` 不进入 AI 修复 Prompt。
7. 知识库计划只能生成手工说明，永远不能进入 AI 写入 Prompt。
8. 依赖知识库的 Skill 修复在人工完成和只读核验前保持阻塞。
9. 现有普通反馈优化流程和确认门禁不退化。
10. 使用 BG8169、300673 及至少一个同时包含知识库和 Skill 缺口的案例回归。

## 14. 完成判据

- 用户能从 HTML 首页看出 AI 与人工的整体差距。
- 用户能从每条 `L-*` 追溯到材料证据、执行链根因和具体 `FIX-*`。
- 用户能从每个 `FIX-*` 反查它解决的全部人工独有事项。
- 知识库修复单具体到文档、锚点、修改结构和联动登记，且只能由人工执行。
- Skill 修复 Prompt 具体到批准 ID、文件、动作、依赖和验证，可直接复制给 AI。
