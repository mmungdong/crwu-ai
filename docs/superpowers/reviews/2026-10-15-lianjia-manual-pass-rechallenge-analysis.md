# 链家人工通过后 AI 继续又被验证：专项分析

> 历史诊断快照，日期：2026-10-15。用户已明确确认：在插件打开的同一个浏览器窗口里，人工验证和搜索可以通过，AI 继续后再次被拦。本轮分析当前源码并做离线动作回放，未修改业务实现或操作真实链家会话。

## 结论

应优先修复人工通过之后的页面接管流程。当前实现没有“绑定原标签页、只读当前已通过页面”的完整通道；恢复、取页、截图都可能重新导航，验证码失败又被外层连续重试。

这些行为已在源码或离线动作回放中确认，可能解释用户现象。本轮尚未捕获真实链家在每一步的响应，因此不能认定某一次导航、标签选择或请求频率就是唯一触发原因，也不能承诺改完后所有自动访问都会放行。

## 已确认的动作问题

| 环节 | 当前实现 | 对本次现象的影响 |
| --- | --- | --- |
| 人工继续 | `resume` 仍调用 `recover`，策略为 `auto` | 没有单独的人工完成后只读检查路径 |
| CLI 恢复 | 先 `Navigate(target)`，再检查页面 | 可以重新访问原地址，丢开人工已经通过并显示的页面 |
| 恢复后取数 | 恢复称成功后，transport 再次 `fetchOnce` | 产生又一次页面请求，而不是读取恢复后的当前页面 |
| fetch / shot | `runAction` 总是 `Navigate(opt.URL)` | 读页面和截图都附带再次访问，不能复用一次已通过的页面快照 |
| 标签页选择 | 附着取第一个 `type=page` 的调试目标 | 同浏览器、同 profile 仍不能保证接管员工验证的那个标签页 |
| 验证失败 | provider 抛普通 Error，外层最多连试三次 | 丢失验证码分类，增加被拦后的重复请求 |
| 候选截图 | 房源循环里使用列表页 URL | 多个候选重复导航、截图同一个列表页 |
| 详情取证 | capture 仍可能走原始 HTTP fetch | 无法复用人工验证的浏览器页面上下文 |

## 推荐方案

```text
任务遇验证
  → 保存项目 / 方案 / 页面任务，保留原浏览器和标签页
  → 暂停该来源的自动请求
  → 员工在这个标签页完成验证，页面返回实际搜索或详情结果
  → 员工点击“继续”
  → Host 附着登记的原标签页
  → 读取当前 URL、页面身份、业务字段和验证状态，不导航、不刷新
  → 校验通过：保存当前 DOM 与正式截图
  → 从当前页面的实际链接进入下一项必要任务
       ├─ 正常：继续
       └─ 再遇验证：保存该任务并等待人工
```

具体改动：

1. **增加只读当前页的取证能力**。CLI/Host 区分导航与读取，当前页读取和截图不隐含 `Page.navigate`。当前地址仍须满足任务的站点、城市、小区或房源身份要求，防止把其他标签页当成成功。
2. **绑定标签页，不只绑定 profile**。Host 内部保留对应任务的浏览器与页面标识；恢复附着时选择这个页面。标签页已关闭、页面身份改变时明确报出，不能改选第一个页面。
3. **区分人工继续与自动恢复**。人工继续只核验当前页；验证尚未通过时继续等待，不再调用不匹配的自动解题策略。
4. **验证码单次遇到即暂停**。保留结构化失败类型、实际页面、恢复任务标识、已完成证据。429 遵守服务端 `Retry-After`；其余可重试错误按独立预算处理。
5. **一次页面读取同时完成留证**。列表页只留一次检索证据；采用候选的详情按各自房源身份读取与截图。缓存同一任务的有效结果，避免反复打开相同页面。
6. **全部链家取证沿同一浏览器通道**。详情工具不得悄悄降级到另起 HTTP 请求；不要导出 Cookie、验证票据或会话凭据来另建通道。
7. **按业务足够停止**。达到知识要求的候选数量后停止拓展。单来源受控排队与缓存是减少无效访问的措施，没有官方保证免验证的固定间隔。

## 最小现场验证顺序

员工完成一次验证后，依次做三个独立检查，记录非凭据页面事实：

| 检查 | 预期 | 若重新被拦，应查哪里 |
| --- | --- | --- |
| 只读取原标签页当前 DOM | 没有重新导航；身份和业务字段正确 | 标签附着、页面选择、当前页读取实现 |
| 同页截图 | 没有刷新；图片仍为原业务页面 | 截图是否隐含导航，以及页面是否被其他任务改动 |
| 沿实际链接进入一条详情 | 最多一次必要页面访问 | 页面级风控或访问限制；保存该详情任务并转人工 |

这样能够区分“接管错误”“读图时重复请求”和“进入下一页又被站点要求验证”。本轮未对用户的真实浏览器执行这些检查，现场验收仍是最后一环。

## 可立即使用的替代工作方式

如果修复前需要继续估值，员工可以在已经通过的浏览器中手动选择实际案例，保存可用的页面或截图，再让 AI 从本地材料中提取和核对。每案保留完整来源 URL、采集时间、稳定房源身份、价格性质与证据关联；验证页和兜底页不作为案例证据。资料能否作为可比案例仍按本轮知识判定。

这个方式适合本次少量案例需求。持续或批量数据需求应向平台确认授权数据渠道；平台服务政策将异常抓取纳入可能触发访问处理的行为。本轮未确认存在可直接接入本项目的公开房源 API。[贝壳服务政策](https://www.ke.com/zhuanti/serviceProtocol)

## 本轮证据与限制

离线动作回放调用当前模块，观察到：

```text
人工继续：recover(url=原任务 URL, strategy=auto)
恢复成功链路：fetch → recover → fetch
验证码失败：同一分页实际取页 3 次
```

Go 源码确认恢复、fetch、shot 都存在强制导航；标签发现器不按任务页面选择。上述结果证明程序动作，没有独立证明链家当时具体依据哪个信号拒绝自动访问。

当前候选自动策略主要适配极验 v3，源码也没有真实页面成功验收保证。用户运行记录中的 hip 页面与这一策略不匹配；本专项的目标是保留人工已经通过的上下文并减少重复访问。HTTP 429 的等待应遵守服务端提示。[MDN：429](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/429)
