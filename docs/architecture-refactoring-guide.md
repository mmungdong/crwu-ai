# 架构重构与公共 UI 开发参考

状态：维护中的目标架构与渐进迁移参考，尚未全量落地。

首次整理：2026-10-22。适用于 `crwu` 仓库，重构重点为 `plugins/dsh-crwu-workbench`。

本文件供后续 Agent 设计功能、拆分模块、提取公共组件和整理样式时参考。目标目录不代表当前目录；现状以任务所在工作树的源码、测试和最近一级 `AGENTS.md` 为准。每次只实施用户任务涉及的迁移范围，本文件不授权一次性重写项目，也不授权提交、推送或发布。

## 1. Agent 使用顺序

1. 阅读根目录、`plugins/` 和插件内适用的 `AGENTS.md`，核对工作树及已有变更。
2. 找到本次功能的业务所有者，阅读实际调用链和现有测试；用第 3 至第 5 节确定依赖方向。
3. 涉及公共组件或样式时，执行第 6 节的所有权规则，并阅读当前 UI 规范。
4. 按第 7 节选择一个可独立验证的迁移单元，写清输入、输出、兼容性和验收范围后实施。
5. 按第 8 节验证，交付时说明已迁移内容、保留的兼容入口和未验证事项。

完成标准：本次改动有明确所有者、依赖方向和验证证据；无需为了匹配目标目录而迁移无关模块。

## 2. 架构选择与范围

采用**按业务能力组织的模块化单体，核心业务使用 DDD 建模，外部能力通过端口和适配器接入**。Host 与 Client 保持独立构建及现有插件发布形态。

| 路线 | 取舍 |
| --- | --- |
| 保留横向目录，补依赖约束 | 适合作为第一步，能限制新增耦合，但同一业务仍横跨多个目录。 |
| 按业务模块纵向组织，逐步提炼领域模型 | 推荐目标；让规则、用例和适配器有共同业务所有者，支持分批迁移。 |
| 拆成多个发布包或独立服务 | 等存在独立消费、部署或发布需求后再评估。 |

DDD 的判断依据是业务语言、规则和一致性边界。实体、聚合和值对象可以用类型与纯函数实现；根据需要引入仓储接口或领域事件，不以 class 数量作为验收条件。CQRS、事件溯源、通用事件总线和通用 Repository 不属于本轮默认目标。

Go CLI 继续遵守现有 `transport → app → integrations` 边界。CLI 与插件通过明确的命令和输出契约协作；TypeScript 领域重构不要求同步改造 Go 包结构。

## 3. 业务模块与候选领域模型

### 3.1 模块归属

业务模块是代码所有权单位；限界上下文还需根据业务语言、规则及一致性要求确认，不能直接由当前目录推导。

| 能力 | 定位 | 所有权 |
| --- | --- | --- |
| 报告审核 `report-audit` | 核心业务模块 | 审核轮次、材料范围、停止与重启、交付规则。 |
| 报告评估 `report-evaluation` | 核心业务模块 | 估值项目、运行修订、问卷、证据准入、结果确认。 |
| 本地审核 `local-audit` | 暂时独立的业务模块 | 本地快照、交接、认领、本地交付限制。 |
| 环境、授权、更新、工作空间清理 | 支撑模块 | 能力探测、授权收据、更新生命周期、清理确认。 |
| 文件、命令代理、网络、凭据存储 | 技术机制 | 平台访问与执行机制，承载现有安全边界。 |
| H3Yun、DWS、OSS、iFinD | 外部提供方 | 提供方协议、调用、DTO 和错误转换。 |

本地审核和报告审核先保持独立。只有确认业务语言与生命周期规则一致后，才提取共同规则或调整上下文；页面相似不足以证明可以合并。

知识获取、浏览器采集、市场检索和交付处理按职责分解：来源选择、证据准入、交付完整性属于业务规则；网络请求、页面访问、下载、上传和文件读写属于适配器。多个模块实际复用且语义一致的技术能力，才提升为公共实现。

跨模块调用经过显式的应用接口或端口；调用方不得直接读取另一模块内部状态、注册表或持久化结构。跨模块流程由应用编排或组合根连接，提供方集成之间保持独立。

### 3.2 候选模型与约束

以下名称是建模起点，最终聚合边界在迁移对应用例时确认。

| 候选概念 | 含义 | 应集中保护的约束 |
| --- | --- | --- |
| 估值运行 `ValuationRun` | 一次可修订、可恢复的估值执行 | 命令基于当前修订；旧结果不能覆盖新输入；停止未确认时保留写入占用。 |
| 输入快照 `InputSnapshot` | 本轮采用材料的确定身份与摘要 | 已冻结输入的变化可被识别，不以未验证的本地副本代替远端读取失败。 |
| 证据池 `EvidencePool` | 已观察并经准入的来源和样本集合 | 来源可验证，样本有效，模型候选通过准入后才进入受控计算。 |
| 审核运行 `AuditRun` | 一轮审核及其执行与停止状态 | 未确认子会话静止前，不释放占用或启动替代运行。 |

领域规则表达“什么操作合法”；跨请求、实例或恢复过程中的互斥和版本提交由应用层与存储机制共同保证。迁移时根据实际运行模型选择串行化、锁或条件写入，保持现有并发安全，不能只移动一个版本判断函数。

“用例”表示一次完整业务动作，例如修订输入；“端口”表示用例需要的窄能力；“适配器”把端口连接到框架、提供方或持久化实现；“线协议 DTO”表示 Host/Client 交换的数据，不等同于领域模型。

## 4. Host 与共享契约

### 4.1 目标目录

以下树相对于仓库根目录，是按需演进的目标。简单模块只建立实际需要的层，不创建空目录或占位抽象。

```text
plugins/dsh-crwu-workbench/src/
├── shared/
│   ├── contracts/
│   └── utils/
├── host/
│   ├── bootstrap/
│   ├── modules/
│   │   ├── report-evaluation/
│   │   │   ├── domain/
│   │   │   ├── application/
│   │   │   ├── ports/
│   │   │   └── adapters/
│   │   │       ├── operations/
│   │   │       ├── tools/
│   │   │       ├── persistence/
│   │   │       └── workflow/
│   │   ├── report-audit/
│   │   └── local-audit/
│   ├── integrations/
│   ├── platform/
│   └── support/
└── client/
    ├── app/
    ├── shell/
    ├── platform/
    ├── modules/
    ├── ui/
    └── styles/
```

### 4.2 依赖规则

```text
入站适配器（Operations / Tools） → application → domain
                                      ↓
                                    ports ← 出站适配器

bootstrap 创建实例、注入实现并管理生命周期。
Host 和 Client 分别依赖 shared/contracts。
```

| 层 | 内容与允许依赖 | 边界 |
| --- | --- | --- |
| `domain` | 业务状态、值对象、纯规则、业务错误 | 环境无关；不导入 DSH、Cordis、LangGraph、I/O、适配器或 wire DTO。 |
| `application` | 启动、修订、取消、交付等用例；依赖领域与端口 | 使用业务输入输出，保持提供方与框架无关。 |
| `ports` | 用例需要的能力接口，可使用领域类型 | 不暴露提供方 DTO、框架 Context 或 LangGraph checkpoint 类型。 |
| `adapters` | Operations、Tools、持久化、流程引擎及业务专属集成 | 完成协议校验、类型映射、端口实现和错误转换。 |
| `integrations` | 独立提供方客户端及协议 | 不导入其他提供方；业务专属编排留在业务模块适配器。 |
| `platform` | 文件、命令代理、凭据等机制 | 不引用业务模型或依赖业务注册表。 |
| `bootstrap` | 实例、依赖、注册与释放 | 可以引用各层公开入口，保持装配职责。 |
| `shared` | 中立协议、协议校验、协议常量、公共纯函数 | 不引用 Host 或 Client，包括 type-only 导入。 |

Operations 与模型可见 Tools 调用同一套应用用例。两者各自的鉴权、scope、校验和输出脱敏继续由所属边界执行；提取用例不得绕过现有 broker、Tool 注册或策略管线。

业务节点定义、依赖关系和失效传播依据语义归入领域或应用层；LangGraph 图编译、checkpoint 和恢复驱动归流程适配器。避免把整个旧 `graph/` 目录机械迁入某一层。

### 4.3 当前代码的迁移方向

以下锚点已在目标工作树核对，执行迁移前仍应重新阅读：

| 当前入口 | 迁移方向 |
| --- | --- |
| [估值 workflow/service.ts](../plugins/dsh-crwu-workbench/src/host/domains/report-evaluation/workflow/service.ts) | 分离业务状态变更、应用用例和图驱动，先迁移一个完整用例。 |
| [valuation-workflow 集成](../plugins/dsh-crwu-workbench/src/host/integrations/valuation-workflow/) | 按实际职责归入估值模块适配器或应用层；提供方无关能力再独立提取。 |
| [Host 操作装配](../plugins/dsh-crwu-workbench/src/host/operations/register.ts) | 模块提供操作表，装配层统一组合；已实现操作声明从实际注册表推导，并检测重名。 |
| [共享 wire 契约核对](../plugins/dsh-crwu-workbench/src/shared/wire/report-audit.ts) | 将内部模型到 DTO 的映射及编译期核对迁到 Host 适配器或契约测试。 |

公共契约独立定义请求、响应和结构化失败，领域与 DTO 在适配器显式转换。保留必要的契约校验，避免把领域模型整体暴露给 Client。跨进程字段或行为变化按插件规则升级协议；仅移动内部文件不自动构成协议变化。

案例访问检查等跨业务策略通过明确的 scope 查询能力组合，保留现有拒绝规则。不要因为原实现位于审核目录，就让审核模块继续了解所有其他模块的注册表；也不要另建一套绕过现有授权机制的公共服务。

## 5. Client 分层与公共能力

### 5.1 分工

| 层 | 所有权 |
| --- | --- |
| `app` | 模块装配、页面注册、依赖连接、语言资源组合、生命周期及样式组合。 |
| `shell` | 面板框架、导航、侧栏、页面容器与切换，不管理各业务的完整工作流。 |
| `modules/<业务>` | 该业务的 API、模型、控制器、草稿、轮询、动作及业务组件。 |
| `platform` | RPC、宿主服务适配、打开会话和选择目录等公共能力。 |
| `ui` | 公共展示组件与通用交互，只通过明确 props 和回调承接业务。 |
| `styles` | 公共主题、基础规则、作用域及样式安装机制。 |

依赖方向：`app` 组合 Shell、模块和平台实现；Shell 通过页面或导航描述接收业务入口；业务模块使用公共 UI、平台接口与共享协议。公共 UI、平台机制都不反向导入业务模块或 Shell。

模块专属端口由模块拥有，实现可在模块适配器或应用装配处连接。真正通用的能力契约才归平台层；不能仅移动现有 `shell/services.ts`，却保留其对审核模块内部类型的依赖。

当前 [WorkbenchPanel.tsx](../plugins/dsh-crwu-workbench/src/client/shell/WorkbenchPanel.tsx) 应逐步收薄为页面容器；各模块管理自己的业务加载与操作。环境事实继续复用现有环境模型和导航状态，避免在每个模块另算一套就绪条件。

模块通过小而明确的公开入口导出页面、控制器和所需类型。语言资源按所属模块拆分后在应用层组合；公共控件文案有独立所有者，不依赖整份业务文案集合。

### 5.2 公共组件抽取

公共组件能在不加载特定业务模块的情况下，通过 props 独立渲染和交互。业务语义仍由业务包装组件解释，例如“审核风险等级”到通用 Badge 外观的映射。

优先整理现有实现：Button、IconButton、FormField、输入控件、Select、DatePicker、Popover，以及 Card、Section、Badge、Loading、SideDrawer、WorkflowWorkspace、StructuredValue。保留已有行为和可访问性能力，避免重写一套平行组件库。

每个组件拥有实现、props、类名、样式及测试。可沿用当前组件与 `ui/styles/` 分离的布局，也可逐步共置；关键是唯一所有权和稳定导出，不要求一次性更换所有组件路径。

```text
ui/components/Button/
├── Button.tsx
├── classes.ts
└── styles.ts
```

[primitives.tsx](../plugins/dsh-crwu-workbench/src/client/ui/primitives.tsx) 和 [SideDrawer.tsx](../plugins/dsh-crwu-workbench/src/client/ui/SideDrawer.tsx) 当前引用 Shell 类名，抽取时由组件接管。旧 props 或导入路径需要兼容时使用薄转出，禁止保留两份实现，并在本次交付中登记后续移除条件。

先完成插件内部复用。只有出现第二个稳定消费者，并明确主题适配、构建和发布责任后，才提升为跨插件公共包。

## 6. 公共样式、组件样式与业务样式

### 6.1 所有权

| 类别 | 应包含 | 所有者 |
| --- | --- | --- |
| 公共主题 | 宿主主题映射，通用颜色、文字、间距、圆角和层级变量 | 公共 token 模块。 |
| 公共基础 | 插件作用域、盒模型、少量通用基础规则 | 公共样式基础层。 |
| 组件样式 | 控件外观、内部布局、交互与禁用等状态 | 对应组件或其专属样式文件。 |
| Shell 样式 | 面板骨架、导航、侧栏、滚动容器 | Shell。 |
| 业务样式 | 业务页面排版、区域布局和专属语义 | 对应业务模块。 |

组件通过 props、插槽、变体或明确约定的 CSS 变量接受定制。业务容器负责组件之间的间距和位置，避免依赖组件内部 DOM、重定义公共控件外观或逐层叠加选择器权重。

### 6.2 保持现有交付机制

保留 TS 样式文本、统一作用域、单一安装入口以及 Cordis 生命周期释放，与现有单文件 Client 产物兼容。公共样式以插件作用域为边界，不向宿主 `body` 或 `:root` 注入插件主题变量。

当前 [styles/bundle.ts](../plugins/dsh-crwu-workbench/src/client/styles/bundle.ts) 已统一组合各所有者样式；所有权拆分和唯一装配入口可以共存。以后迁入 `app` 时保留兼容入口，并同步更新引用和测试，不新增第二个安装通道。

保留现有作用域前缀、选择器权重、明暗主题、独立挂载点及样式节点引用计数。抽取组件时检查样式依赖闭包：组件连同其公共依赖可独立渲染，且无需估值或审核模块提供 CSS。

### 6.3 首批整理对象与 token 迁移

- [base.ts](../plugins/dsh-crwu-workbench/src/client/styles/base.ts) 中的面板头部归 Shell，加载页面规则归对应组件或初始化页面。
- [估值 workflow 样式](../plugins/dsh-crwu-workbench/src/client/modules/report-evaluation/styles/workflow.ts) 中属于 [WorkflowWorkspace](../plugins/dsh-crwu-workbench/src/client/ui/workflow/WorkflowWorkspace.tsx) 和 StructuredValue 的通用规则，随公共组件迁出。
- 业务专属变量在设计上由业务模块拥有；公共交互变量继续由公共主题拥有。

当前强制规范仍以 [styles/tokens.ts](../plugins/dsh-crwu-workbench/src/client/styles/tokens.ts) 为唯一字面量颜色所有者。第一批迁移保持该约束；未来拆分业务 token 时，在同一任务中同步修改 UI 规范、所有者清单、字面量检查和主题测试后再切换，避免形成互相冲突的两套规则。

迁移先保持样式组合顺序和视觉表现。若要调整层叠策略、主题值或采用新的 CSS 构建方案，作为明确的独立设计变更处理。

## 7. 渐进迁移顺序

以下是推荐先后关系，不是已经完成的实施计划。每批先核对用户任务范围，再确定具体文件和测试。

| 阶段 | 工作内容 | 完成标准 |
| --- | --- | --- |
| P0：边界门禁 | 建立 Host、Client、shared 的依赖检查；冻结现有违规依赖。 | 注入一条新增违规依赖会失败；存量例外可追踪；扫描文件数非零。 |
| P1：公共 UI 样板 | 以 SideDrawer、WorkflowWorkspace 为切口整理实现、类名、样式和公共依赖。 | 独立渲染、主题、焦点、关闭和卸载行为通过；公共 UI 不依赖 Shell 或业务模块。 |
| P2：Host 用例样板 | 以估值“修订输入”为切口提取规则、应用用例及执行和存储端口。 | 保留版本、占用、证据与结果失效语义；应用用例可使用假端口验证；原入口继续可用。 |
| P3：逐模块推广 | 迁移其他用例，收薄 WorkbenchPanel，整理公开入口、注册和文案。 | 新功能只触及必要模块及装配点；兼容入口有明确移除条件。 |

边界检查应解析真实导入目标，覆盖相对路径、别名、type-only 导入、转出和可静态解析的动态导入。例外至少登记来源、目标、原因及移除条件；不能只比较违规总数，因为删除旧违规可能掩盖新增违规。测试专用的跨层契约核对使用明确规则，运行时代码边界保持独立。

每批先建立能证明原行为的测试；发生行为变化时先证明新增断言按预期失败，再实施。纯路径迁移保留行为测试并运行相关门禁，不为搬文件编写只复述新路径的测试。

更新路径时一并检查源码、测试、脚本、构建和按目录扫描的守卫。守卫必须证明仍能扫描目标文件，防止迁移后“零文件、永远绿”。

## 8. 验收与交付

### 8.1 按变更选择验证

| 改动 | 验证证据 |
