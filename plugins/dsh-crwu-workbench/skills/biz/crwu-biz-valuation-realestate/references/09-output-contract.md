# 09 · 输出契约（案例目录、项目索引、报告数据、HTML 与底稿）

本轮的**全部产物只写在估值案例目录里**。技能目录（含 `template/`、`schemas/`、`examples/`）
是**只读**的：任何情况下都不许回写，产物一律落案例目录。

## 案例目录（协议 35）

**项目级**事实只有一份，**方案级**交付件各自一份（`方案/<planId>/`）。一个项目可以有多个
方案（住宅 + 商业、房地分别评估的土地/建筑物组件…），把它们的交付件混在根目录会让
`crwu_valuation_finalize` 读到**别的方案**的报告数据并判成完成 —— 因此方案级文件一律带方案目录。

```text
<已选工作区>/<项目 ID>/
  材料-源/                     原始资料（Host 复制进来，带 sha256 清单）
  知识快照/                    本轮实际取到的知识正文（项目级；来源记录里带 planId）
    知识来源/<routeId>.json    逐路由的来源记录（schema 合规，routeId 在顶层）
    .知识来源.json             Host 汇总索引（finalize 读它）
  提取结果/                    资料提取的完整结果
    提取-<文件名>.json         单份提取结果（正文 / 表格 / `pages` 逐页文本层 / `capabilities` 能力声明）
    提取-<文件名>-页面图片/    无文本层页导出的**内嵌位图**（内容未识别；`path` 相对本目录，见 workflow.md §二之一）
    提取汇总.json              Host 汇总（正文、表格、图像数量、缺口；逐页表与能力声明读单份 JSON）
  估值输入.json               确认抽屉确认时**冻结**的输入（方法/评估目的/价值类型/基准日/补充要求/资料清单/指纹）
  项目估值方案索引.json        项目 → 方案 → 对象 + 方法判定 + 执行任务图
  方案/plan-001-住宅/          **一个方案一个目录**（planId 由 Host 铸号）
    来源证据/页面/             该方案的外部页面证据（页面字节 + 内容指纹）
    推理结果/
      图片/<caseId-名称>/      该方案的页面截图证据（**挑战页截图永远不放这里**）
        图片清单.json          截图证据清单（路径 / 指纹 / 有效性与原因）
    估值对象.json             规范化后的评估对象（fields / missingFields / sourceRefs）
    估值案例.json             候选案例（来源、链接、时间、挂牌或成交、保留剔除理由）
    估值参数.json             参数与税率取值及依据（**全部来自本轮知识快照**）
    模板验真.json             计算表模板的 id / 指纹 / 期望指纹 / 结构校验结论
    重算结论.json             工作簿重算记录（谁重算、核对了什么、有没有不一致）
    估值报告数据.json         受约束的报告数据（HTML 的唯一数据源）
    估值报告.html             人读的方案报告（按固定模板渲染）
    估值底稿.xlsx             由知识库模板复制后填写的计算表（多对象时逐对象一份）
    产物清单.json             交付件清单（哪些存在、哪些缺、缺的原因）
  估值报告.html               项目入口报告（汇总各方案正文；可以只有中断说明）
```

中断的方案同样要有自己的方案目录（`估值状态.json` + 报告数据 + 中断 HTML），
**只是没有金额结论与正式 result/底稿** —— "这个方案没有目录"与"这个方案被阻断"是两件事。

`估值输入.json` 是**不可变**的：它由 Host 在确认那一刻写死，子会话只能读。
方法、评估目的、价值类型、基准日与用户补充要求都取自它，子会话没有参数能改写。
**未指定**的字段是 `null`（不是空串、更不是某个默认结论）：`baseDate` / `purpose` / `valueType`
为 `null` 时，报告与结果必须**逐字**写明「本次未指定…」，且不得据此声称正式估值已完成。
finalize 会**重算**冻结输入的摘要与宿主记录比对：对不上就判 `failed`（不是"以文件为准"）。

## 项目 → 方案 → 对象（不是"一轮一对象"）

| 层 | 是什么 | 拆分依据 |
| --- | --- | --- |
| 项目 | 一条父估值会话对应的全部工作 | — |
| 方案（`plan`） | **同一个口径的一批对象** | 物业类型、评估目的、价值类型、权益口径、基准日、市场范围 |
| 对象（`object`） | 一宗具体的房地产 | 房号 / 用途 / 面积 / 权证 |

**原始登记用途与业务分类是两个字段**（P15）：

| 字段 | 是什么 | 口径 |
| --- | --- | --- |
| `registeredUse` | 原始权证 / 登记用途（资料原文） | 只许照抄资料，读不到就是空串 |
| `propertyType` | 本轮知识规则下的**业务分类** | 必须由 `classificationBasis` 支撑 |
| `classificationBasis` | 业务分类的依据（登记用途 / 规划用途 / 实际使用 + 资料坐标） | 空 = 依据缺失 |

- **名称不是依据**：名称里出现「公寓」「公寓式住宅」等字样**不构成**分类依据，
  **不得**因此套用住宅模板；
- **依据缺失就挂起该对象**（不进方案、不算结论），**其余对象照常继续** ——
  既不按名字猜一个分类，也不因为一个对象没核清就让整轮停摆；
- 挂起是 `GroupingOutcome.suspendedObjectIds` + `valuation.grouping.unclassified-object`
  阻断项，必须逐条列给员工（缺什么、查过哪、怎么补）。

硬性规则（违反即判不合格，见 `validateGrouping`）：

- 一个对象**只能属于一个方案**：一个对象出现在两个方案里 → 冲突；
- **住宅与商业必须拆方案**（物业类型取对象自己的识别结果，不取方案的措辞）；
- 同一方案内，评估目的 / 价值类型 / 权益口径 / 基准日 / 市场范围**不一致 → 冲突**；
- **价值范围互斥**：`land-only` / `building-only` / `land-and-building` 不许重叠 ——
  重叠就是**同一块价值被算两次**，而两个方案的单价各自看都"合理"；
- 房地分别评估（`separate`）时，土地方案与建筑物方案是**有依赖的一张任务图**；
  **土地能力尚未实现**（本技能不提供）→ 该方案记 `blocked` 并说明缺什么，
  **不创建假能力、不把土地价值并进建筑物**。

## 方法判定（写在 `项目估值方案索引.json`）

1. `method` 只能是 `market` / `income` / `cost`：`auto` 是用户的**输入**，不是结论。
2. **业务不适用**与**当前未实现**是两种状态，分开记：
   - 业务不适用 = 知识正文说不适用该对象（写依据：规范条款 / 资料条件 / 数据充分性）；
   - 未实现 = 业务上适用，但本技能/本部署还没有该方法的完整能力（记能力缺口，不进结论）。
3. 用户指定方法是**约束**：结论与用户指定不一致时**必须**写出 `methodConflict`
   （`userMethod` / `adoptedMethod` / `reason`），没有冲突时显式写 `null`。
   **不许静默切换** —— 要么按用户指定的方法算，要么把冲突与原因写出来并进待确认事项。
   finalize 也会拦这一条：跳过校验脚本同样过不去。
4. 每个方案至少要有一条方法判定；`adopted` 的**集合**必须与结论的 `methods[]` 完全一致
   （协议 39：可以采用**单一或组合**方法）；只写一句"不符合要求"不可复核。
5. **组合方法**：`methods[]` 列出实际采用的全部方法（`methods[0]` = 主方法 `method`）；
   `methodResults[]` 为每个采用方法分别记录依据、参数、案例、模板与结果；
   `methodCoordination` 说明对象结论是怎么协调出来的 ——
   **不许默认平均、不许把同一对象的不同方法相加**（多方法是交叉校核，不是求和）。
   `component-sum` 只能用于范围互斥的组件（土地 / 建筑物），且依据里必须点名组件。
   没有加权依据时 `weights` 必须是 `null`。

## 少案例、候选编号与复算（协议 39）

- **1～2 条可核案例 + 有计算依据**：照常给参考结论、实际案例与**具体限制**，不因为数量少清空金额。
  一条可用依据都没有时与用户沟通，保留已完成的工作，**不伪造金额**、不静默换指定方法。
- **相近但未达标的候选要与达标案例一起列出**，用 `crwu_valuation_revision` 的 `op=candidates` 登记：
  每条给出**稳定编号**（Host 发放、跨轮次不变）、与达标条件的差异、以及纳入后对结论的影响。
  引用候选一律用编号 —— 自己重排编号会让用户说的"3 号"指向另一条房源。
- 用户回复「加入 A、C 重算」时：`op=recompute` 建立**新版本**，默认复用原规则、原模板与已取得的数据
  （**不自动重搜**；补搜或换规则要显式给出新的轮次 / 规则版本）。每一版的交付件落在
  `方案/<planId>/修订/<n>/`（第 1 版是方案根），**旧版报告、底稿与结论原样保留**。
- 写完之后用 `op=promote` 让 Host 对**那一版自己的交付件**跑一次完成判定；
  **通过之前当前版本指针不动**，失败只留一条失败记录（`state = failed`）并保留其编号。

## 少案例：参考结论与"没有结论"（§6.1 / §6.2）

| 情况 | 怎么给 | 为什么 |
| --- | --- | --- |
| 可用案例 ≥ 知识要求 | 正式结论 | —— |
| 可用案例 1~2 条但**有计算依据** | **给参考结论**（照常算单价 / 总价）+ 具体限制：差几条、不得作为正式结论交付 | 清空金额会让复核的人看不到任何可比信息，也看不出差多少 |
| **一条可用依据都没有**（挂牌 / 询价、缺单价…） | 不给金额（`null`）+ 写清为什么 + 与用户沟通 | 没有依据的数字就是编的（§6.2） |

`calculate_market.py` 的结论行带 `provisional` 与 `provisionalReason`：报告与底稿要能一眼看出
"这个数是参考值"，而不是靠读限制段推断。缺额同时进 `ruleChecks`
（`market.comparables.min-adopted` 记 `passed: false`），复核的人能在规则层看到它没过。

## 重算与回读（协议 39）

底稿里的公式**不会自己算**：openpyxl 读回来的是上次保存的缓存值。所以交付前必须真正重算一次：

1. 调 `crwu_valuation_recalculate`，提交「对象 → 数值位置」（`objectId` / `unitPriceCell` /
   `totalValueCell`）。位置按**你实际用的那份模板的填写说明**给 —— Host 不猜格子。
2. Host 用部署配置的表格程序把底稿**打开重算一次**（产物落临时目录，原底稿不动），
   再调 `scripts/read_workbook_values.py` 以 `data_only=True` **回读缓存值**，
   与 `估值报告数据.json` 逐项比对，然后**由 Host 写**`重算结论.json`。
3. `verified` 只有在"回读值与报告数据逐项一致"时才为真。回读不到某对象的数值算**不一致**：
   "读不到"和"对得上"是两件事。

没有配置表格计算程序（`valuation.recalculation.enginePath` 为空）时它返回 `unavailable`：
那就如实交付 `partial` 并标注「待重算」。**不要**自己写一份"重算通过"的结论 ——
finalize 会真实探测本机的表格程序，探测不到时那份记录会被判失败。

## 报告数据（`估值报告数据.json`）—— HTML 的唯一数据源

结构与校验规则见 [`schemas/valuation-report-data.schema.json`](../schemas/valuation-report-data.schema.json)。
这份 JSON 由 `scripts/build_report_data.py` 从运行 manifest 组装，**不许手写、不许另誊数字**。

几条硬性规则（由组装脚本与 finalize 两侧把守）：

1. `baseDate` 为空时，待确认事项里**必须**有「本次未指定评估基准日」。
   **不许**把资料里识别到的日期补成基准日 —— 识别到的东西只能展示为"资料中的日期"。
   同理，`purpose`（评估目的）/ `valueType`（价值类型）为空时，待确认事项里**必须**各有一句
   「本次未指定评估目的」/「本次未指定价值类型」；`limitations[]` 里也要逐字出现。
   **未指定评估目的或价值类型时不得声称 `completed`**（`build_report_data.py` 会直接拒绝组装）。
   可选值清单属于业务规范（`04-参数与税费` 一类的知识正文），技能与脚本里**不写默认枚举**。
2. 每个对象至少要有**一个金额**（`unitPrice` 或 `totalValue`）；拿不到就是 `null`，**不许填 0**
   （`0` 与"没有"是两件事，而 0 会静默把汇总拉低）。`totalValue` 为 `null` 即 `blocked`。
3. 有 `unitPrice` 就**必须**有正数计价面积：`unitPrice × pricingArea ≈ totalValue`（允许 1 元舍入差）。
4. 每条结论都要给 `basisRefs`（`routeId` + `snapshotDigest`）：**结论建立在哪一版规则上**必须可回答。
5. 案例与参数：
   - 每条案例必须有交易类型，且保留 / 剔除理由至少一个非空；
   - `used_as_comparable = true` 的案例**必须**是**成交**。挂牌价是卖方要价、系统性高于成交价，
     直接当成交价会把估值整体抬高 —— 挂牌案例**不得**直接作为可比实例（`calculate_market.py` 会拒绝）；
   - 阈值（单案例修正上限、共同修正上限、组内比值上限、采用案例数下限、取整口径）**只来自本轮知识快照**，
     由调用方显式传入。脚本没有业务默认值：缺参数就报缺口，**不许**自行放宽或补一个"常见值"；
   - 每条参数记录都要能分辨**字段缺失**与**方法所需关键参数缺失**：前者是登记缺口
     （`missingImpact = registration-gap`，其余步骤继续），后者要**挂起相关计算**
     （`calculation-suspended`）。混成一句"资料不全"就分不清"少一栏"与"算不下去"（P17）。
6. `workbooks[]` 要登记相对路径、模板 id 与**模板指纹**；`images` 要登记相对路径与指纹。
7. 能力缺口与待确认事项要**完整**：有缺口却写成"已按规范完成"，比缺一个数字更糟。

## 截图证据（`推理结果/图片/<caseId-名称>/`）

- 目录名是 `<安全 caseId>-<安全 名称>`：身份是 `caseId`，名称只是标签（不能靠文件名反推案例）；
- **挑战页截图永远不是案例证据**：可见人机验证页被判为拦截时，截图通道不产出文件，
  该案例如实写 `screenshot_missing`（绝不拿页面字节或指纹顶替截图）；
- 知识要求截图而清单缺失或指纹不符 → finalize 降级 `partial`。

## 交付前必须过的两道门

```bash
# ① 工作簿契约：按该工作簿自己的填写说明（<workbook>.contract.json / --contract）核对
#    可见表、公式区、结果位、单位与外部链接；没有填写说明就拒绝，不回退内置 profile。
python3 scripts/check_workbook_contract.py <方案目录>/估值底稿.xlsx
# ② 报告数据：按 report-data.v2 Schema 与口径只读校验（不产出）。
python3 scripts/build_report_data.py --validate <方案目录>/估值报告数据.json
```

② **显式 finalize**（不再是"页面还活着就算完成"）：调用 `crwu_valuation_finalize`，
由 **Host** 用真实文件判定状态。它核对：冻结输入摘要（**重算**后比对）、知识快照
（逐条 `routeId` + 指纹，来源只能是 `dws` / `verified-mirror`）、模板验真、逐对象结论、
计算轨迹、截图证据、计算表登记、**重算记录**、报告渲染、产物清单。缺任何一项都会降级
（`completed` → `partial` / `blocked`）并列出逐条问题。

**没有落盘的重算记录时，上限就是 `partial`** —— 绝不用"底稿里有公式"推断"已重算"。
本机没有可用的重算程序（Excel / LibreOffice）时如实标记，**不许**声称正式完成。

**所有数字结论以重算后的工作簿为准**：报告与报告数据里的数字必须能从底稿的公式重算得到；
两者不一致时以底稿为准并修报告，而不是改底稿去凑报告。

### 「三者一致」到底查到哪一步（能力边界，别误读）

| 两两 | 查到什么 | 怎么查 |
| --- | --- | --- |
| 报告 HTML ↔ 报告数据 JSON | **严格**：HTML 由这份 JSON 按固定模板渲染，数字不另誊 | `build_report.py` 渲染 + 图片边界/指纹校验 |
| 报告数据 JSON ↔ 底稿 | **方法严格 + 结构存在性**：结论的方法与逐对象金额必须能在底稿对应位置找到 | `check_workbook_contract.py` + finalize |
| 底稿数字 ↔ JSON 数字 | ⚠️ **本机查不了**：比较需要**重算后的**单元格值，而组装脚本不算公式 | 交付前必须真打开一次底稿让它重算，并落 `重算结论.json` |

最后一格是**已记录的能力缺口**，不是"已经查过了"。所以规矩是：重算之后**由人核对**一次
汇总表的结论与报告数据是否一致；本机的自动检查保证的是"口径（方法与结构）一致 + 数字没写错地方"。

## 挂牌参考交付（listing-reference，一次性）

挂牌参考是**参考口径**，不是正式结论：它只做「原始挂牌报价的算术平均」，不做修正 / 折扣。交付走
**一条命名 Tool**，不要自己拼脚本或脚手架：

- **固定输入**：`方案/<planId>/挂牌参考输入.json`（`revision > 1` 时为
  `方案/<planId>/修订/<n>/挂牌参考输入.json`）；路径由 Host 从已登记方案派生，模型提交不了任意路径。
- **一条调用**：`crwu_valuation_listing_reference { caseDir, planId, revision? }` —— 参数面只有这三个。
  Host 只接受本轮估值会话与已登记方案；输入里的 `valuationMode` / `projectId` / `planId` 必须与本轮一致。
- **四件产物**（都在该方案的输入目录下）：`计算轨迹.json` / `估值底稿.xlsx` /
  `估值报告数据.json` / `估值报告.html`；四件都要真实存在且非空，缺一件即结构化失败。
- **状态只可能是 `partial`**：报告与底稿都必须显式标注「挂牌参考，未作修正 / 折扣，不得作为正式结论交付」。
  **不存在** `completed` 这一档，也不因为没有正式模板 / Excel 引擎就跳过这道标注。
- **能力缺口**：本部署没有配置好的 DSH Python 时，Tool 回 `capability-gap`；不得改走 shell / 手工命令。

## HTML 报告

报告至少要能回答：评估对象是谁、评估目的与价值类型、基准日、采用的方法与理由、关键参数与取值依据、
单价与总价、待确认事项、能力缺口、知识来源清单、案例清单（含来源与时间）与**截图证据**。
报告是一次性渲染的人读件，**不参与**计算；数字一致性的权威是底稿。
