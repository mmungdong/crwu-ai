# PRD · 中瑞世联工作台 · 侧栏三模块

> 状态：**v1 已实施**（实施记录与真机验收见 §9）· 日期：2026-09-22 · 版本基线：插件 0.0.4

## 1. Summary

把「中瑞世联工作台」从**一个入口 + 面板内切换**改成**左侧侧边栏里直接排开三个子项**：
报告评估、报告审核、环境信息。员工打开 DSH 就能一眼看到这三个入口，点哪个进哪个，
不用先进面板再找底部那一行模块条。

## 2. Contacts

| 名字 | 角色 | 关注点 / 意见 |
| --- | --- | --- |
| 用户（产品负责人） | 需求方、验收方 | 「这三个是中瑞世联工作台的子模块，相当于一个小单元」；要**一眼可见**，不要藏在面板里 |
| 插件维护者（我） | 设计与实现 | 侧栏席位能力、模块状态共享、首次进入规则、测试与真机验收 |
| 员工（评估/审核岗） | 使用者 | 打开就能用；知道自己该点哪个；没配置好时知道怎么办 |

## 3. Background

- 现在工作台常驻在**左侧栏底部**（`sidebar.footer.action`，Settings 上方）**只有一个条目**；
  进去以后靠面板**底部的模块条**在三个模块之间切。
- 员工反馈：三个模块是"小单元"的三个面，应该在**侧栏就看见**，而不是进去再切。
- 现在**正好是这个时机**：`报告评估 / 报告审核 / 环境信息` 三个模块刚拆出来
  （`src/client/features/workbench/modules.ts` 是它们的单一事实源），报告评估是占位页，
  侧栏结构怎么定，决定后面所有模块的入口形态 —— 越晚改，越多人已经形成习惯。

### 3.1 现实约束（已用运行时真凭据查过，不是推测）

DSH 侧栏可加的席位只有两个，且都是**平铺列表**：

| 席位 | 位置 | 能做什么 |
| --- | --- | --- |
| `sidebar.panellist` | 侧栏**顶部**图标区（全局面板入口） | 可加任意多条条目（id + order + label） |
| `sidebar.footer.action` | 侧栏**底部**、Settings 旁 | 同上 |
| `sidebar.workspaces` | 侧栏中部（会话/工作区分组列表） | `single` 席位，**替换即遮挡出厂 UI** —— 不能用来加子项 |

**结论**：没有"分组 + 子项"这种控件可加。于是有两条路（见 §7）：

1. 注册**三条相邻的条目**，靠图标族、命名前缀、固定顺序表达"它们属于同一个工作台"；
2. **只注册一条，内容自绘成一张分组卡**（卡头 + 三行子项）—— 这条路不需要 DSH 提供分组控件，
   形态完全由插件掌控，也是 v1 实际采用的那条（见 §9）。

## 4. Objective

**目标**：员工打开 DSH，在左侧侧边栏**直接**看到「中瑞世联工作台」下的三个入口 —— 报告评估、
报告审核、环境信息 —— 点一次就到位，不用先进工作台再找切换控件。

**为什么重要**：

- 三个模块是日常动作的三个入口，藏在面板底部等于每次多两步（进面板 → 找模块条 → 切）。
- 入口形态一旦定下就影响后续所有模块；现在只占位一个「报告评估」，改动成本最低。

**Key Results（SMART）**：

- KR1：侧栏**一次可见**三个入口；员工从打开 DSH 到进入目标模块的点击次数 ≤ 2（现状 3）。
- KR2：三个入口的名字与顺序在所有状态下固定（含未授权、未自检、报告评估未开发）—— 不因状态重排。
- KR3：折叠成窄栏时，三个入口仍可区分（各有独立图标 + 悬停文字）。
- KR4：真浏览器验收断言覆盖"三个入口都在、顺序固定、点哪个进哪个、窄栏仍有图标"，
  且**不点「AI 审核」**、不产生任何 OSS 列举（除既有的一次）。

## 5. Market Segment(s)

- **一线评估/审核员工**：每天要看「待审核报告」，跑完要取「AI 审核结果」，装完电脑要过「环境信息」。
  他们对"入口在哪"最敏感，也最不愿意记路径。
- **新员工（首次使用）**：第一次装插件，需要先看环境信息（缺什么、怎么配），再开始审核。
  入口必须自解释，不能靠文档。
- **维护者/我**：需要在里面排查问题（环境信息页的「排查详情」），但这是次要入口。

约束：员工机器上不一定有 Node/Python/ossutil；不一定授权过；插件与 DSH 都在快速迭代
（DSH 是 developer preview，席位可能变）。

## 6. Value Proposition(s)

**要解决的工作（Job）**：我要处理一份评估报告的 AI 审核这件事，但我得先知道"从哪儿进"。

- **得到**：侧栏一眼看到三个入口 → 少两步操作；三个名字就是三件事，不需要记。
- **避免的痛**：不再"进去以后找底部那条"；不再因为模块条常驻而挤占正文高度；
  不再出现"我以为工作台只有一页"。
- **比现状好在哪**：把"一个入口 + 内部导航"换成"三个平行入口"，符合 DSH 侧栏
  （顶部图标区）本身的用法：一屏之内，入口即导航。
- **不做什么**：不替换 DSH 出厂侧栏、不动会话列表区（会遮挡出厂 UI，风险不可接受）。

**价值曲线对比**（相对现状）：

| 维度 | 现状（单入口 + 面板内模块条） | 本方案（侧栏三条目） |
| --- | --- | --- |
| 入口可见性 | 低（要进面板） | 高（打开即见） |
| 到达步数 | 3 | ≤2 |
| 导航一致性 | 两套（侧栏 + 面板底） | 一套 |
| 正文可用高度 | 被模块条占一条 | 全部给正文 |
| 出厂 UI 风险 | 无 | 无（只用加法席位） |

## 7. Solution

### 7.1 UX / 原型（文字线框）

展开态侧栏（推荐放**顶部图标区** `sidebar.panellist`，与出厂面板入口同类）。
**只注册一个条目，内容是一个"分组卡"**，卡里排三个子项 —— 这样样式完全由插件掌控，
视觉上就是一个模块（Apple 式分组：圆角容器 + 半透明填充 + 细分隔线 + 选中高亮）：

```
┌ 左侧栏 ─────────────────────┐
│ ⌂  会话                      │
│ ──────────────────────────  │
│ ╭──────────────────────────╮ │  ← 一个条目 = 一张分组卡
│ │ ▣ 中瑞世联工作台   v0.0.4│ │     卡头：品牌 + 名字 + 版本/状态
│ ├──────────────────────────┤ │
│ │ ◧ 报告评估          开发中│ │  ← 占位；灰态但**位置固定**
│ │ ◨ 报告审核           ● 就绪│ │  ← 默认落地页（自检通过时）
│ │ ◩ 环境信息           ●     │ │  ← 自检不通过时停这里
│ ╰──────────────────────────╯ │
│ ──────────────────────────  │
│ ⚙  设置                      │
└─────────────────────────────┘
```

- **分组卡**：`border-radius` 中圆角 + 一层浅填充（主题变量）+ 卡头与子项之间一条 1px 分隔线；
  三个子项之间用更浅的分隔线；当前所在模块用"选中底色 + 左侧 3px 强调条"表达。
- **三个子项各自一行**：图标 + 名字 + 右侧状态（`● 就绪` / `● 未通过` / `开发中`）；
  整行可点、悬停有轻微底色变化（Apple 侧的 hover 惯例）。
- **颜色只用 DSH 主题变量**（`--dsw-alias-bg-layer-*`、`--dsw-alias-border-l1`、
  `--dsw-alias-label-*`、`--dsw-alias-state-success|error|warn-primary`），亮/暗自动跟随，不写死色值。
- **窄栏（折叠）态**：卡片排不下三行 → 降级为**一颗只有品牌标记的图标**（**不画**环境标记，见 §9.11）；
  悬停出文字（含环境结论），点它直接把面板切到当前模块。窄栏绝不出现"三行挤成一列"的破版。

> 样式必须是"加法"的：只在插件自己渲染的元素上生效，不改出厂侧栏的容器样式。

进入规则（沿用已确认口径）：**环境自检通过 → 默认落在报告审核；不通过 → 落在环境信息**；
员工手动切过之后不再自动跳走。若未授权，先由授权弹框挡住（已有实现），授权后可继续。

### 7.2 Key Features

1. **一个侧栏条目 = 一张分组卡 + 三个子项**（视觉上是一个模块，结构上只有一个席位占用）：
   - **卡头** `中瑞世联工作台`：品牌标记 + 名称 + 版本小标签；它是"这组属于谁"的锚点，
     点击进入默认模块。
   - **子项 1 `报告评估`**：固定位置，右侧「开发中」角标；点进去是占位页（说明将做什么，
     不提供假功能）。
   - **子项 2 `报告审核`**：待审核报告 / AI 审核结果（含按流水号查找）；右侧显示状态点。
   - **子项 3 `环境信息`**：环境自检四层 + AK 表单 + 排查详情；右侧显示状态点。
   - 状态点在卡内复用同一份环境结论（和面板里的结论必须一致）。
2. **三个模块共用一份状态**：版本标签、环境结论、授权状态由外壳统一持有并下发，
   三个入口看到的是**同一个结论**（不允许出现"入口说就绪、页里说没通过"）。
3. **去掉面板内的底部模块条**：侧栏已经是唯一导航，两套导航会互相干扰、也白占正文高度。
4. **状态可见**：环境入口带状态点（绿=就绪 / 红=未通过 / 黄=自检中）；`报告评估` 带「开发中」；
   其它两个不带装饰。**折叠轨道上不带任何状态标记**（收起来时那枚绿勾只是噪音，见 §9.11）。
5. **不改变既有门禁**：环境不通过仍拦住"发起审核"；未授权仍先弹授权框。

### 7.3 Technology（要点，不是实现细节）

- 席位：**`sidebar.footer.action`（底部、Settings 上方），只占一条**（内容自绘分组卡）。
  位置沿用 2026-09-22 用户当面确认的口径（工作台常驻在侧栏底部，工作区留在它上方）；
  `sidebar.panellist`（顶部图标区）与工作台"常驻工具"的定位不符，v1 不再使用。
- 分组卡样式：插件在自己的组件里画（圆角 + 浅填充 + 分隔线 + 选中高亮），只用 DSH 主题变量；
  自己的类名走 `crwu-audit-` 前缀 + 自有 `<style>` 注入，**不碰出厂侧栏的容器样式**。
- 兜底方案（若出厂条目外壳自带底色/内边距导致卡片观感被破坏）：退成**三条相邻条目**，
  用"首条上圆角 / 中间直角 / 末条下圆角"的连续圆角 + 同色底，拼出同一张卡的效果 ——
  真机截图对比后选更像"一个模块"的那个。
- 内容列：三个模块**共用** `main` 上的一个 keyed 席位（`crwu-workbench`），由一份共享的
  模块状态决定画哪一页 —— 三页共用同一个外壳（头部、授权门槛、抽屉、提示条），
  拆成三个席位就会把外壳复制三份。
- 状态与授权：仍走现有 `envStatus` / `build` 存储；协议号只在跨进程契约变化时 +1。
- 图标：新增三个 `crwu-audit-` 前缀之外的**侧栏图标**（矢量内联，不引外部依赖）。

### 7.4 Assumptions（待验证）

- A1：出厂侧栏的条目外壳允许插件自绘底色/圆角（不被上层底色盖住、不被内边距切掉）→
  需真浏览器截图确认；不行就走 §7.3 的兜底方案（连续圆角拼卡）。
- A2：分组卡的"一个模块"观感（Apple 式）是否达到预期 → 需用户看真机截图拍板。
- A5：窄栏降级为单图标后员工仍能认出工作台 → 真浏览器断言窄栏态。
- A3：DSH 后续版本不会改变这两个席位的语义（developer preview）→ 用加法席位降低风险，
  并把"席位名 + 顺序"写进测试，漂移时立刻红。
- A4：去掉面板底部模块条不会让任何人"找不到切换"（因为有侧栏）→ 由用户真机确认。

## 8. Release

- **v1（第一版，本轮已完成）**：**一个席位 = 一张分组卡 + 三个子项**（卡头 + 三行，顺序固定）+
  三模块切换（侧栏与面板共用一份状态）+ 去掉面板底部模块条 + 状态点/角标 + 选中态 +
  真浏览器断言（几何上"三行在同一张卡里"、顺序、选中态、全页只有这三行）+ 单元测试与证伪。
  报告评估仍是占位页。
- **v2（后续）**：报告评估的**真实内容**（由用户给口径后再做：这页展示什么、能做什么操作）。
- **v3（可选）**：入口上的即时信息（如待审核条数），以及"最近打开的模块"记忆。

时间上不做承诺（DSH 与插件都在快速迭代）；v1 是"一次改动 + 一次真机验收"的体量。

## 9. 实施记录（v1，2026-09-22）

### 9.1 落地形态：分组卡（不是三条相邻条目）

- 席位仍是 `sidebar.footer.action` **一条**，内容自绘：`.crwu-audit-side-card`（浅底圆角卡）
  = 卡头（品牌标记 + 「中瑞世联工作台」+ 版本标签）+ 三行 `.crwu-audit-module` 子项。
- 样式只加在插件自己的元素上，**不碰出厂侧栏容器**：卡底 `--dsw-alias-bg-layer-2`、描边
  `--dsw-alias-border-l1`、选中行浅底 + `inset 3px 0 0 var(--dsw-alias-brand-primary)` 强调条
  （用 inset 阴影而不是 border/padding —— 行内文字不会因为选中而左右跳一格）。
- 模块状态上移为 `src/client/features/workbench/module-store.ts`，由 `apply()` 创建并**同时**
  下发给侧栏卡与面板：`active`（当前模块）、`autoEntered`（只自动落位一次）、
  `selectEpoch`（用户每次主动选都 +1，面板靠它清掉上一次的自检拦截态）、
  `badge`（待办条数，由面板推给侧栏子项）。用测试断言两边拿到的是**同一个对象**
  （`registrations[0].component().props.modules === registrations[1].component().props.modules`）。
- 面板里的 `ModuleSwitcher`（底部模块条）与其全部类名/样式一并删除：两套导航会互相干扰，
  也白占正文高度；模块名改由面板头部显示，待办条数移到侧栏子项右侧。

### 9.2 真机验收（一次性 profile，不动用户的 3080）

- 一次性 profile `smoke-side`（`dsh --profile smoke-side --from-default-profile web`
  + `dsh plugin --profile smoke-side add <repo>`），端口 3099，`cd /Users/mungdong` 启动；
  验完删 profile。
- **A1（出厂条目外壳会不会破坏卡片观感）：不成立 → 不需要 §7.3 的兜底方案。** 真机截图里
  分组卡完整（圆角、底色、卡头、三行子项都在），出厂侧栏没有给它叠底色、也没有切边距，
  所以没有理由退回"三条相邻条目 + 连续圆角"。
- **几何证据**（`boundingBox`，1440×900）：卡 `x=12 y=706 w=256 h=138`；
  三行 `x=17 w=246 h=32`，`y=741 / 774 / 807` —— 三行都落在卡的范围内、自上而下排列，
  即"看起来是一个模块"的可观察判据。截图见 `install/browser-check.mjs` 产出的
  `sidebar-card.png` / `sidebar-modules.png`。
- 顺手修掉验收脚本的一处**假失败**：它原先靠正文里「环境就绪 / 环境未通过」等自检结论，
  而自检通过时面板会直接跳到「报告审核」，带那句话的环境信息页常常根本不出现 ——
  改成等**侧栏子项上那枚标记的结论色**（常驻、稳定）。

### 9.3 门禁与证伪

- `make plugin-check` 全绿（版本/配置/技能/`tsc`/单元测试/构建/产物冒烟/打包自检/dist 守卫自检）；
  单元测试 **463 条全过**（其中新增 `tests/unit/client-module-store.test.mjs` 3 条与
  侧栏卡/模块切换若干条断言）。
- **证伪过三次**（每条新断言都至少红过一次）：把子项裁成两行 → "三行 + 顺序固定"红；
  让子项点击不写 store → "点子项必须真的把模块切过去"红；让 `apply()` 给面板另造一份 store
  → "侧栏分组卡与面板要共用同一份模块状态"红。
- 真浏览器验收 `install/browser-check.mjs` 在 3099 上全过（含新增的"分组卡"阶段：
  三行子项、固定顺序、都在同一张卡里、自上而下、点过的子项是选中态、全页只有这三行入口），
  控制台零报错，全程**没有**发出 `audit-start`。

### 9.4 v1 返工：用户看图后提的三条（同日）

用户在自己的 3080 上看了 v1 的截图/界面后提了三条，都属**视觉与可点性**，不改结构：

| # | 用户原话 | 根因 | 改法 |
|---|---|---|---|

| 页面 | 顶部摘要说「还需完成 N 项」；iFinD 步骤显示「待处理」 |
| 测试 | 旧口径断言逐条改写（"只有 iFinD 缺失时是 degraded" / "iFinD 不拦导航" / "required=false" / "externalData 永远为 true" / "就绪时显示进入报告审核按钮"） |

`degraded` 枚举保留给将来真正的可选能力，但**不再由"只有 iFinD 缺失"产生**。

#### 二、真实外部验证：OSS 与 iFinD 各打一次真请求

- **OSS**：`ossutil ls oss://<bucket>/<配置前缀>/ --endpoint <配置> --limited-num 1`，只读、空目录也算
  成功、不再打桶根（只验桶根证明不了"能写交付件"）。失败结构化归因四类
  （`credential` / `permission` / `config` / `infrastructure`），四类给四种不同的员工动作。
  探测输出与上传错误共用 `host/oss/sanitize.ts` 的脱敏器。
- **iFinD**：`initialize → notifications/initialized → tools/list → 选安全只读工具 → tools/call`。
  只有 `tools/call` 返回非错误、非空内容才 `dataVerified=true`；`ok`（认证）与 `dataVerified`（取数）
  分开显示。四阶段归因一致（`classifyFailure` 先看 401/403 再看消息指纹）。
- OSS 仍按环境检查执行连通性探测；iFinD 只在保存后立刻验或用户点击「重新验证」时复检，
  环境检查显示最近真实验证时间，**不会把本地读取说成刚刚重新请求**。
